# 按需恢复的多来源路由与配额分发边界（v3）

本轮仅审查相对 `HEAD` 的未提交改动，并沿生产装配追踪了 `aggregation.Service → SessionInvoker → manager.Manager → sessionDialer → transport` 的完整链路。`stdioClientConn` 现已将 `WaitClosed` 透传到 SDK 会话，空闲期断连会撤销旧会话注册并交回唯一连接循环；恢复等待也复用了 `SessionInvoker` 的总调用预算，超时会归一化为 `UPSTREAM_TIMEOUT`。已发出的 `tools/call` 在传输失败后不会被透明重放，恢复候选的常规配额预占也已移至恢复完成后的预分发回调。仍有两处中优先级边界使多来源回退和“未分发不计费”的语义不能完全成立。

**Watch for:** **[已确认]** 多个不可用同名来源中只有首个候选会进入恢复流程，首个来源恢复后因额度拒绝或恢复失败时不会回退到其余候选；**[已确认]** 延迟配额回调仍早于实际 `CallTool` 分发，会话可在两者间关闭并消耗未发送请求的额度。

**Verdict**: NEEDS_CHANGES

## High-level view

**[已确认]** 连接恢复本身被收敛到每上游唯一的 `Manager` 循环，stdio 的关闭事件也已可达该循环，因此上轮关于空闲断连、总超时映射和已发送请求重放的修复均已接通。路由层却只将 `recoveryCandidates[0]` 交给调用器；其余候选只被收集，不参与一次调用中的恢复或额度回退，和新增注释承诺的“逐个校验”不一致。

**[已确认]** `PreDispatchInvoker` 将配额判断推迟到了恢复之后，但它在会话快照完成后、真正调用 `CallTool` 之前运行。会话终态检测可以在这个窗口注销并关闭同一会话，使请求未被分发却已占用来源额度。

## 同名上游只恢复首个候选，额度拒绝会截断路由回退

`internal/aggregation/aggregation.go` 在遍历来源时将所有不可用且可恢复的来源追加到 `recoveryCandidates`，注释明确说明后续应逐个通过配额校验；但循环结束后固定取 `recoveryCandidates[0]` 并返回。`InvokeTool` 随后只对这个候选调用一次 `CallUpstreamWithPreDispatch`。当该来源恢复成功但 `reserveCandidateQuota` 返回限流错误时，`preDispatchReservationError` 被立即解包并返回；当该来源在总调用预算内无法恢复时，也同样结束本次调用。列表中剩余的兼容来源从未被尝试。

因此，两个均暂不可用的同名来源中，来源 A 可以恢复但额度已满、来源 B 可以恢复且有额度时，调用仍返回 `RATE_LIMITED`；来源 A 恢复超时而来源 B 已恢复时，也仍返回 A 的失败结果。这个行为使新引入的按需恢复路径比原有可用来源遍历更早停止，并违背代码中“不能错过另一个可以立即恢复并执行的同名来源”的设计意图。修复需要让恢复候选成为可迭代的路由序列：每个候选在共享的调用总预算内等待一次其对应连接、在实际分发前预占一次额度，只有已向上游分发后才停止回退，避免对有副作用的请求重放。

新增测试覆盖了单一恢复候选成功以及单一恢复失败不占额，但未覆盖多个不可用候选中的“首个额度拒绝 / 首个恢复失败，后续候选可执行”场景。

## 会话关闭可发生在配额回调和真正分发之间

`SessionInvoker.callUpstream` 在恢复后获得 `session`，执行 `beforeDispatch(callCtx)`，随后才启动调用 `session.CallTool` 的协程。与此同时，`internal/app/adapters.go` 中的 `dialedConn.Wait` 可因 SDK 生命周期结束或另一条 RPC 报告会话终态而调用 `markBroken`；连接循环接着执行 `Close`，而 `baseSession.Close` 会将会话置为关闭并释放底层连接。

这建立了确定的并发顺序：调用路径已持有旧 `dialedConn` 指针 → `beforeDispatch` 通过并递增配额 → 生命周期路径注销并关闭该会话 → `CallTool` 仅返回 `ErrSessionLost`/不可用，工具请求没有发送。`reserveCandidateQuota` 没有回滚，聚合层也把该错误作为来源失败记录，而不是继续尝试另一来源。缓冲结果通道避免了调用协程阻塞，但并不能使这段配额与发送之间的空档原子化。

应将“确认当前会话仍可分发、预占配额、启动一次 `CallTool`”置于 `dialedConn` 的同一受管分发临界区，或让调用器返回可区分的“未发送即失效”结果并回滚预占。只要工具调用已经开始发送，就应继续保持当前的不重放策略。
